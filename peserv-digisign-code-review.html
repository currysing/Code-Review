HighF-02: Endpoints are explicitly anonymous

Plain-English explanation. [AllowAnonymous] tells ASP.NET to let requests through even when the rest of the application requires authentication. That can be valid for health checks and login callbacks, but it is dangerous on endpoints that issue certificates, update user/corporate records, process signing callbacks, or return sensitive data. Every anonymous endpoint needs its own strong proof that the caller is legitimate, such as mTLS or a verified HMAC signature.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • peserv-digisign/src/DPOCorpID.Core/Controllers/PdfSigningController.cs:10 [AllowAnonymous]
  • peserv-digisign/src/DPOCorpID.Core/Controllers/DigiSignProxyController.cs:17 [AllowAnonymous]
  • peserv-digisign/src/DPOCorpID.Core/Controllers/DigisignController.cs:11 [AllowAnonymous]
  • peserv-digisign/src/DPOCorpID.Core/Controllers/ConsentController.cs:11 [AllowAnonymous]

Why it matters. Anonymous controller actions are risky when they perform business, signing, onboarding, administration, callback, or proxy operations.

Recommended fix. Review every AllowAnonymous usage. Keep only health and externally required callbacks, and protect callbacks with mTLS/HMAC/replay controls.

MediumF-03: Swagger/OpenAPI appears enabled in committed configuration or runtime code

Plain-English explanation. Swagger publishes a browsable list of API endpoints and request/response schemas. That is useful for developers, but in production it helps attackers discover hidden or sensitive routes quickly, especially when some endpoints are weakly protected.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • peserv-digisign/src/DPOCorpID.Core/appsettings.Development.json:43 "OpenSwagger": true,

  • peserv-digisign/src/DPOCorpID.Core/appsettings.json:46 "OpenSwagger": true,

Why it matters. Public API documentation can expose sensitive endpoint and model details, especially when combined with weak auth.

Recommended fix. Disable Swagger in production or protect it with admin authentication and network restrictions.

SOLID Design Review

This is a static design review against the SOLID principles. It focuses on source structure, class/module size, layering, and dependency direction; it does not prove runtime behavior.

Overall SOLID posturePartially aligned. Controllers, services, repositories, DTOs, and security-related helpers are separated, but high-value flows still collect many steps in large service classes.
Evidence reviewedThe backend scan found 4 controllers, 8 service-oriented files, and 8 repositories. Largest files include src/DPOCorpID.Services/Services/ConsentService.cs (605 lines), src/DPOCorpID.Services/DTOs/Requests/SigningRequests.cs (421 lines), src/DPOCorpID.Services/Services/DigisignService.cs (404 lines).
Design strengths
  • Layered backend structure separates HTTP, application service, repository, and model concerns.
  • Security and integration concepts are visible as separate services in several areas.
  • Existing test projects in this family create a path for contract-preserving refactors.
Principle-specific pressure points
  • Single Responsibility. Form filling, consent, signing, crypto, and callback flows should be decomposed when a service coordinates validation, persistence, external calls, and response building.
  • Open/Closed. New channel/client variants should be added through strategy/adaptor classes rather than expanding conditionals inside central services.
  • Interface Segregation. Split service interfaces around use cases so controllers and tests do not depend on broad service surfaces.
  • Dependency Inversion. High-level flows should depend on interfaces for crypto, external clients, repositories, and clocks/options.
Recommended refactoring pathRefactor one high-risk flow at a time into validators, command/use-case services, external-client ports, and response mappers. Preserve behavior with unit tests before splitting large services.
