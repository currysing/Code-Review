CriticalF-01: JWT validation is disabled or claims are decoded without validation

Plain-English explanation. a JWT is only trustworthy after the server verifies who issued it, who it was meant for, whether it is expired, and whether its signature matches a trusted signing key. Code such as ReadJwtToken only opens the token and reads the text inside; it does not prove the token is genuine. Similarly, settings like ValidateIssuer = false or RequireSignedTokens = false tell the framework to skip important checks. In this codebase, the finding surfaces where startup code disables JWT validation flags, or where helper code decodes bearer tokens and then uses claims such as user id, role, session id, or jti. A forged token can contain any claims an attacker chooses, so those claims must not drive identity or authorization unless validation has already succeeded.

Why it matters. Forged or expired tokens can be accepted or used for user context if code trusts unvalidated claims.

Recommended fix. Require issuer, audience, lifetime, and signing-key validation outside local-only diagnostics. Do not drive authorization from ReadJwtToken-decoded claims.

MediumF-02: Swagger/OpenAPI appears enabled in committed configuration or runtime code

Plain-English explanation. Swagger publishes a browsable list of API endpoints and request/response schemas. That is useful for developers, but in production it helps attackers discover hidden or sensitive routes quickly, especially when some endpoints are weakly protected.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

Why it matters. Public API documentation can expose sensitive endpoint and model details, especially when combined with weak auth.

Recommended fix. Disable Swagger in production or protect it with admin authentication and network restrictions.

SOLID Design Review

This is a static design review against the SOLID principles. It focuses on source structure, class/module size, layering, and dependency direction; it does not prove runtime behavior.

Overall SOLID postureMixed. The SDK exposes shared base repositories, base services, AOP/interceptor infrastructure, utilities, and security services. These abstractions help reuse, but the largest base classes are large enough to become inheritance-heavy coupling points.
Evidence reviewedThe backend scan found 1 controller, 17 service-oriented files, and 2 repositories. Largest files include shared/Framework.Core/Base/BaseRepository.cs (1864 lines), shared/Framework.Core/AOP/Autofac/UnifiedInterceptor.cs (1677 lines), shared/Framework.Core/Base/BaseService.cs (1613 lines).
Design strengths
  • Shared framework layers create common extension points for repository, service, security, and audit-log behavior.
  • Centralized interceptors and utilities reduce duplicate cross-cutting code across downstream services.
Principle-specific pressure points
  • Single Responsibility. Large base classes such as shared/Framework.Core/Base/BaseRepository.cs and shared/Framework.Core/Base/BaseService.cs risk collecting unrelated persistence, mapping, validation, and orchestration behavior.
  • Liskov Substitution. Deep inheritance in base services/repositories can make subclasses depend on implicit base behavior that is hard to substitute safely.
  • Interface Segregation. Shared framework interfaces should stay narrow; broad base contracts push all consumers to accept methods they may not need.
  • Dependency Inversion. Cross-cutting services should expose small interfaces so applications depend on contracts rather than concrete framework utilities.
Recommended refactoring pathSplit large base classes by capability, prefer composition for optional behavior, document subclass contracts, and add contract tests for shared abstractions before changing downstream services.
