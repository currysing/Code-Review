CriticalF-02: Controllers are mapped without visible authentication middleware

Plain-English explanation. the service starts accepting controller routes, but the normal ASP.NET authentication and authorization pipeline is not visible in the startup file. That means the code itself does not prove callers must be logged in before reaching business endpoints. If a gateway is supposed to protect it, the service is still fragile because direct internal access or an ingress mistake can bypass that assumption.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • intf-crird/DPOCorpID.Core/Program.cs:29 app.MapControllers();

Why it matters. Business endpoints may be callable without identity checks if the service is reachable directly or through a misconfigured gateway.

Recommended fix. Configure authentication and authorization in the service, add a fallback authorization policy, and explicitly mark only health or verified callback endpoints as anonymous.

Plain-English explanation. Swagger publishes a browsable list of API endpoints and request/response schemas. That is useful for developers, but in production it helps attackers discover hidden or sensitive routes quickly, especially when some endpoints are weakly protected.

SOLID Design Review

This is a static design review against the SOLID principles. It focuses on source structure, class/module size, layering, and dependency direction; it does not prove runtime behavior.

Overall SOLID postureMixed. The projects show service/repository/controller layering, but interface-integration classes often become large orchestration points that combine external protocol handling, transformation, persistence, crypto, and retry/failover behavior.
Evidence reviewedThe backend scan found 5 controllers, 11 service-oriented file, and 13 repositories. Largest files include DPOCorpID.Services/Interface/CRService.cs (1672 lines), DPOCorpID.Services/Interface/CheckRpService.cs (1090 lines), DPOCorpID.Services/Interface/IRDService.cs (665 lines).
Design strengths
  • Controllers, services/interfaces, and repositories are separated into recognizable layers.
  • External integration concerns are visible as named services, which is better than hiding them inside controllers.
  • Repository classes provide a boundary for persistence changes.
Principle-specific pressure points
  • Single Responsibility. Large integration services should be split by protocol client, request mapping, validation, persistence, and retry/failover responsibilities.
  • Open/Closed. New external interface variants should plug in through adapters instead of adding conditionals to existing service methods.
  • Liskov Substitution. External client adapters should expose consistent timeout, error, and retry semantics so one integration can be replaced without caller-specific branches.
  • Interface Segregation. Avoid broad integration service contracts; callers should depend only on the operation set they use.
  • Dependency Inversion. Business services should depend on external-service interfaces, not concrete SOAP/HTTP/crypto helper implementations.
Recommended refactoring pathIntroduce small ports for external systems, move mapping/validation into dedicated classes, keep retry/failover policies separate, and cover each adapter contract with focused unit tests.
