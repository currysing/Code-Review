CriticalF-02: JWT validation is disabled or claims are decoded without validation

Plain-English explanation. a JWT is only trustworthy after the server verifies who issued it, who it was meant for, whether it is expired, and whether its signature matches a trusted signing key. Code such as ReadJwtToken only opens the token and reads the text inside; it does not prove the token is genuine. Similarly, settings like ValidateIssuer = false or RequireSignedTokens = false tell the framework to skip important checks. In this codebase, the finding surfaces where startup code disables JWT validation flags, or where helper code decodes bearer tokens and then uses claims such as user id, role, session id, or jti. A forged token can contain any claims an attacker chooses, so those claims must not drive identity or authorization unless validation has already succeeded.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • corpsap-cmain/DPOCorpID.Core/Program.cs:50 ValidateIssuer = false,
  • corpsap-cmain/DPOCorpID.Core/Program.cs:51 ValidateAudience = false,
  • corpsap-cmain/DPOCorpID.Core/Program.cs:52 ValidateLifetime = false,
  • corpsap-cmain/DPOCorpID.Core/Program.cs:53 ValidateIssuerSigningKey = false,
  • corpsap-cmain/DPOCorpID.Core/Program.cs:54 RequireSignedTokens = false

Why it matters. Forged or expired tokens can be accepted or used for user context if code trusts unvalidated claims.

Recommended fix. Require issuer, audience, lifetime, and signing-key validation outside local-only diagnostics. Do not drive authorization from ReadJwtToken-decoded claims.

HighF-04: Debug or test endpoints are present in deployable code

Plain-English explanation. debug endpoints are usually built to help developers inspect state or simulate privileged flows. They often skip normal safeguards. If they remain compiled into deployed services, an attacker or curious internal user may use them to reveal secrets, create mock security material, test downstream connectivity, or trigger operations outside the normal business path.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

SOLID Design Review

This is a static design review against the SOLID principles. It focuses on source structure, class/module size, layering, and dependency direction; it does not prove runtime behavior.

Overall SOLID posturePartially aligned. The codebase follows a familiar Controllers/Services/Repositories split, which supports SOLID at a high level, but larger services and repositories indicate responsibilities are still grouped by entity or module rather than narrow use cases.
Evidence reviewedThe backend scan found 6 controllers, 6 service-oriented files, and 20 repositories. Largest files include DPOCorpID.Services/Services/TmplService.cs (838 lines), DPOCorpID.Services/Services/SysMainNotiService.cs (732 lines), DPOCorpID.Services/Services/AdmBdOfficerService.cs (584 lines).
Design strengths
  • Controllers, service classes, repositories, DTOs, and models are separated into layers.
  • Repository classes create a persistence boundary that can be mocked or replaced when interfaces are kept narrow.
  • The structure gives a clear place to introduce validators, mappers, and external-client adapters.
Principle-specific pressure points
  • Single Responsibility. Large service/repository files suggest business orchestration, validation, mapping, persistence calls, and external interactions may be combined.
  • Open/Closed. New business variants should be introduced through strategy/use-case classes instead of growing switch/if chains in existing services.
  • Liskov Substitution. Shared base repository/service patterns need clear contracts so derived classes remain safely replaceable.
  • Interface Segregation. Avoid broad service interfaces that expose unrelated module operations to every controller.
  • Dependency Inversion. Controllers should depend on application interfaces; services should depend on repository/client abstractions and injected configuration, not concrete helpers.
Recommended refactoring pathStart with the largest service or repository in this project, split validation/mapping/external calls into dedicated collaborators, keep public interfaces use-case sized, and add focused tests before and after each split.
