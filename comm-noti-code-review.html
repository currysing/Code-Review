CriticalF-02: Controllers are mapped without visible authentication middleware

Plain-English explanation. the service starts accepting controller routes, but the normal ASP.NET authentication and authorization pipeline is not visible in the startup file. That means the code itself does not prove callers must be logged in before reaching business endpoints. If a gateway is supposed to protect it, the service is still fragile because direct internal access or an ingress mistake can bypass that assumption.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • comm-noti/DPOCorpID.Core/Program.cs:12 app.MapControllers();

Why it matters. Business endpoints may be callable without identity checks if the service is reachable directly or through a misconfigured gateway.

Recommended fix. Configure authentication and authorization in the service, add a fallback authorization policy, and explicitly mark only health or verified callback endpoints as anonymous.

MediumF-03: Swagger/OpenAPI appears enabled in committed configuration or runtime code

Plain-English explanation. Swagger publishes a browsable list of API endpoints and request/response schemas. That is useful for developers, but in production it helps attackers discover hidden or sensitive routes quickly, especially when some endpoints are weakly protected.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • comm-noti/DPOCorpID.Core/appsettings.Development.json:35 "OpenSwagger": true, // Enable Swagger UI
  • comm-noti/DPOCorpID.Core/appsettings.Production.json:33 "OpenSwagger": true, // Enable Swagger UI

  • comm-noti/DPOCorpID.Core/appsettings.json:33 "OpenSwagger": true, // Enable Swagger UI

Why it matters. Public API documentation can expose sensitive endpoint and model details, especially when combined with weak auth.

Recommended fix. Disable Swagger in production or protect it with admin authentication and network restrictions.

SOLID Design Review

This is a static design review against the SOLID principles. It focuses on source structure, class/module size, layering, and dependency direction; it does not prove runtime behavior.

Overall SOLID posturePartially aligned. The codebase follows a familiar Controllers/Services/Repositories split, which supports SOLID at a high level, but larger services and repositories indicate responsibilities are still grouped by entity or module rather than narrow use cases.
Evidence reviewedThe backend scan found 1 controller, 1 service-oriented file, and 7 repositories. Largest files include DPOCorpID.Services/Services/NotiService.cs (279 lines), DPOCorpID.Services/Repositories/SampleUserRepository.cs (231 lines), DPOCorpID.Services/Repositories/UserPermissionRepository.cs (87 lines).
Design strengths
  • Controllers, service classes, repositories, DTOs, and models are separated into layers.
  • Repository classes create a persistence boundary that can be mocked or replaced when interfaces are kept narrow.
  • The structure gives a clear place to introduce validators, mappers, and external-client adapters.
Principle-specific pressure points
  • Single Responsibility. Large service/repository files suggest business orchestration, validation, mapping, persistence calls, and external interactions may be combined.
  • Open/Closed. New business variants should be introduced through strategy/use-case classes instead of growing switch/if chains in existing services.
  • Liskov Substitution. Shared base repository/service patterns need clear contracts so derived classes remain safely replaceable.
  • Interface Segregation. Avoid broad service interfaces that expose unrelated module operations to every controller.
  • Dependency Inversion. Controllers should depend on application interfaces; services should depend on repository/client abstractions and injected configuration, not concrete helpers.
Recommended refactoring pathStart with the largest service or repository in this project, split validation/mapping/external calls into dedicated collaborators, keep public interfaces use-case sized, and add focused tests before and after each split.
