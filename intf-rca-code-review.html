CriticalF-02: JWT validation is disabled or claims are decoded without validation

Plain-English explanation. a JWT is only trustworthy after the server verifies who issued it, who it was meant for, whether it is expired, and whether its signature matches a trusted signing key. Code such as ReadJwtToken only opens the token and reads the text inside; it does not prove the token is genuine. Similarly, settings like ValidateIssuer = false or RequireSignedTokens = false tell the framework to skip important checks. In this codebase, the finding surfaces where startup code disables JWT validation flags, or where helper code decodes bearer tokens and then uses claims such as user id, role, session id, or jti. A forged token can contain any claims an attacker chooses, so those claims must not drive identity or authorization unless validation has already succeeded.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • intf-rca/Filters/AccessTokenFilter.cs:88 ValidateIssuer = false,
  • intf-rca/Filters/AccessTokenFilter.cs:89 ValidateAudience = false,

Why it matters. Forged or expired tokens can be accepted or used for user context if code trusts unvalidated claims.

Recommended fix. Require issuer, audience, lifetime, and signing-key validation outside local-only diagnostics. Do not drive authorization from ReadJwtToken-decoded claims.

HighF-03: Endpoints are explicitly anonymous

Plain-English explanation. [AllowAnonymous] tells ASP.NET to let requests through even when the rest of the application requires authentication. That can be valid for health checks and login callbacks, but it is dangerous on endpoints that issue certificates, update user/corporate records, process signing callbacks, or return sensitive data. Every anonymous endpoint needs its own strong proof that the caller is legitimate, such as mTLS or a verified HMAC signature.

SOLID Design Review

This is a static design review against the SOLID principles. It focuses on source structure, class/module size, layering, and dependency direction; it does not prove runtime behavior.

Overall SOLID postureMixed. The projects show service/repository/controller layering, but interface-integration classes often become large orchestration points that combine external protocol handling, transformation, persistence, crypto, and retry/failover behavior.
Evidence reviewedThe backend scan found 4 controllers, 15 service-oriented files, and 3 repositories. Largest files include Services/eSignService.cs (882 lines), Services/ManualVettingService.cs (628 lines), Helper/RcaCryptoHelper.cs (387 lines).
Design strengths
  • Controllers, services/interfaces, and repositories are separated into recognizable layers.
  • External integration concerns are visible as named services, which is better than hiding them inside controllers.
  • Repository classes provide a boundary for persistence changes.
Principle-specific pressure points
  • Single Responsibility. Large integration services should be split by protocol client, request mapping, validation, persistence, and retry/failover responsibilities.
  • Open/Closed. New external interface variants should plug in through adapters instead of adding conditionals to existing service methods.
  • Liskov Substitution. External client adapters should expose consistent timeout, error, and retry semantics so one integration can be replaced without caller-specific branches.
  • Interface Segregation. Avoid broad integration service contracts; callers should depend only on the operation set they use.
  • Dependency Inversion. Business services should depend on external-service interfaces, not concrete SOAP/HTTP/crypto helper implementations.
Recommended refactoring pathIntroduce small ports for external systems, move mapping/validation into dedicated classes, keep retry/failover policies separate, and cover each adapter contract with focused unit tests.
