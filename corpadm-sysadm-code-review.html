MediumF-01: Client-side auth state and route guards require backend enforcement

Plain-English explanation. a frontend route guard only hides screens in the browser. Users can still edit JavaScript, change browser storage, or call backend APIs directly. Storing bearer tokens and user profile data in sessionStorage or localStorage also means any XSS bug can read and exfiltrate them. The backend must enforce every permission even if the frontend UI tries to hide unauthorized pages.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

Why it matters. Browser storage and route metadata are not security boundaries. XSS can steal stored tokens/profile data, and unguarded routes can reveal workflow details.

Recommended fix. Keep backend authorization authoritative, reduce token/profile storage in the browser, add CSP, and remove hardcoded client-side access gates.

SOLID Design Review

This is a static design review against the SOLID principles. It focuses on source structure, class/module size, layering, and dependency direction; it does not prove runtime behavior.

Overall SOLID posturePartially aligned. The project has recognizable Vue separation through views, components, stores, composables, router, and API modules, but several large view components suggest multiple responsibilities remain in single files.
Evidence reviewedThe frontend scan found 67 Vue single-file components and 48 TypeScript modules. Largest files include src/views/e-service-provider/e-service/EspEServiceDetail.vue (2649 lines), src/views/e-service-provider/e-service/EspAddEServiceDetail.vue (2493 lines), src/utils/Services/modules/adm-client.ts (1685 lines).
Design strengths
  • API access is grouped under src/utils/Services, which helps keep HTTP concerns out of every component.
  • Pinia stores and composables provide natural dependency and state boundaries when used consistently.
  • Shared components under src/components create extension points for repeated UI behavior.
Principle-specific pressure points
  • Single Responsibility. Large .vue files combine rendering, form state, validation, API orchestration, and workflow branching; this makes change impact harder to isolate.
  • Open/Closed. Repeated workflow-specific pages are easier to extend when variant behavior moves behind composables or small strategy/config modules instead of conditionals inside views.
  • Interface Segregation. Broad API modules can force screens to depend on more operations than they need; narrower feature API clients would reduce coupling.
  • Dependency Inversion. Components should depend on composables or service facades rather than importing low-level HTTP helpers directly.
Recommended refactoring pathPrioritize extracting large page files into presentation components, workflow composables, typed API facades, and validation modules. Add component/composable tests before refactoring the largest screens.
