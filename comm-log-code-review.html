CriticalF-01: Committed credentials or key material

Plain-English explanation. the project contains passwords, client secrets, access keys, private-key material, or certificate passwords in files that are part of the repository. Source-controlled secrets are not private. Anyone with a clone, backup, CI artifact, or leaked archive can read them. Even if a value is intended for development, teams often reuse it or accidentally deploy it.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • comm-log/src/AuditLogWeb/appsettings.Development.json:105 "AccessKey": "admin",
  • comm-log/src/AuditLogWeb/appsettings.Development.json:106 "SecretKey": "admin12345",
  • comm-log/src/AuditLogWeb/appsettings.DciDevelopment.json:113 "AccessKey": "ZMICU6SLADZCQI9DN3GN",
  • comm-log/src/AuditLogWeb/appsettings.DciDevelopment.json:114 "SecretKey": "M9HXRpw1m2NmjmiKwDHamIcvj6wFo3trIxFViWpc",

Why it matters. Credentials or key material in source control should be treated as exposed. This can enable database, Redis, OAuth, certificate, or internal-service compromise if the repository or artifacts are shared.

Recommended fix. Rotate affected secrets, remove them from source control, and load values from environment variables, deployment secrets, or a vault. Add secret scanning to CI.

CriticalF-02: JWT validation is disabled or claims are decoded without validation

Plain-English explanation. A JWT is only trustworthy after the server verifies who issued it, who it was meant for, whether it is expired, and whether its signature matches a trusted signing key. In comm-log, the code reads the bearer token with ReadJwtToken(). That method only decodes the token text; it does not prove that the token came from the real OAuth server or that it has not expired. The decoded claims are then used to set audit identity fields such as UserId, SessionId, and Jti. In practice, a caller could craft a token containing any user id and make the audit log attribute the event to that fake user.

How it surfaces in this project. The flow is: the insert endpoint calls ApplyAuditIdentityFromBearer(); that helper calls JwtBearerAuditIdentityReader.TryRead(HttpContext); the reader decodes the token with ReadJwtToken(); then the controller copies decoded claim values into the audit log object. I did not find a matching AddAuthentication() / validated JWT bearer pipeline in this project that would make these claims trustworthy before use.

Current comm-log JWT Identity Flow

1. HTTP requestCaller sends Authorization: Bearer ... to the insert endpoint.
→
2. ControllerInsertAuditLog() calls ApplyAuditIdentityFromBearer().
→
3. Decode onlyReadJwtToken() reads claims but does not validate signature, issuer, audience, or expiry.
→
4. Claims trustedUserId, SessionId, and Jti are copied into the audit record.

Risk path: a forged bearer token can contain a fake user id, and the audit log can record that fake identity.

Safer Target Flow

1. HTTP requestBearer token arrives.
→
2. ASP.NET JWT authValidate signature, issuer, audience, and expiry.
→
3. Authenticated principalUse HttpContext.User only after validation succeeds.
→
4. Audit identityCopy validated claims into the audit record.
  • comm-log/src/AuditLogWeb/Controllers/AuditLogController.cs:62 ApplyAuditIdentityFromBearer(auditLog); is called during insert.
  • comm-log/src/AuditLogWeb/Infrastructure/JwtBearerAuditIdentityReader.cs:25 var jwt = handler.ReadJwtToken(token); decodes the bearer token without validating it.
  • comm-log/src/AuditLogWeb/Infrastructure/JwtBearerAuditIdentityReader.cs:26 the decoded claims are wrapped into a ClaimsPrincipal as if they were bearer-authenticated claims.
  • comm-log/src/AuditLogWeb/Controllers/AuditLogController.cs:248-253 decoded UserId, SessionId, and Jti values are copied into the audit log.

Why it matters. Audit logs are supposed to be reliable evidence. If the service accepts unvalidated identity claims, a caller can spoof who performed an action, which weakens incident investigation and non-repudiation. This is separate from authorization: even if the endpoint were later protected, this specific code path should read identity from the already-validated HttpContext.User, not from a manually decoded token.

Recommended fix. Configure ASP.NET Core JWT bearer authentication with strict token validation: issuer, audience, lifetime, and signing key. Add app.UseAuthentication() before app.UseAuthorization(). In ApplyAuditIdentityFromBearer(), read claims from HttpContext.User only after authentication succeeds. If upstream services need to submit end-user identity, require a signed service-to-service event contract rather than trusting arbitrary bearer-token text.

MediumF-03: Swagger/OpenAPI appears enabled in committed configuration or runtime code

Plain-English explanation. Swagger publishes a browsable list of API endpoints and request/response schemas. That is useful for developers, but in production it helps attackers discover hidden or sensitive routes quickly, especially when some endpoints are weakly protected.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • comm-log/src/AuditLogWeb/appsettings.DciUat.json:13 "OpenSwagger": true, // Enable Swagger UI
  • comm-log/src/AuditLogWeb/appsettings.Development.json:13 "OpenSwagger": true, // Enable Swagger UI
  • comm-log/src/AuditLogWeb/appsettings.Production.json:13 "OpenSwagger": true, // Enable Swagger UI
  • comm-log/src/AuditLogWeb/appsettings.DciDevelopment.json:18 "OpenSwagger": true, // Enable Swagger UI
  • comm-log/src/AuditLogWeb/appsettings.json:13 "OpenSwagger": true, // Enable Swagger UI

Why it matters. Public API documentation can expose sensitive endpoint and model details, especially when combined with weak auth.

Recommended fix. Disable Swagger in production or protect it with admin authentication and network restrictions.
