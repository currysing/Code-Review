CriticalF-02: JWT validation is disabled or claims are decoded without validation

Plain-English explanation. a JWT is only trustworthy after the server verifies who issued it, who it was meant for, whether it is expired, and whether its signature matches a trusted signing key. Code such as ReadJwtToken only opens the token and reads the text inside; it does not prove the token is genuine. Similarly, settings like ValidateIssuer = false or RequireSignedTokens = false tell the framework to skip important checks. In this codebase, the finding surfaces where startup code disables JWT validation flags, or where helper code decodes bearer tokens and then uses claims such as user id, role, session id, or jti. A forged token can contain any claims an attacker chooses, so those claims must not drive identity or authorization unless validation has already succeeded.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • corpsap-oauth/src/Corpsap.Oauth/Middleware/TokenResponseFilterMiddleware.cs:96 var jsonToken = tokenHandler.ReadJwtToken(accessToken);

Why it matters. Forged or expired tokens can be accepted or used for user context if code trusts unvalidated claims.

Recommended fix. Require issuer, audience, lifetime, and signing-key validation outside local-only diagnostics. Do not drive authorization from ReadJwtToken-decoded claims.

HighF-03: Endpoints are explicitly anonymous

Plain-English explanation. [AllowAnonymous] tells ASP.NET to let requests through even when the rest of the application requires authentication. That can be valid for health checks and login callbacks, but it is dangerous on endpoints that issue certificates, update user/corporate records, process signing callbacks, or return sensitive data. Every anonymous endpoint needs its own strong proof that the caller is legitimate, such as mTLS or a verified HMAC signature.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • corpsap-oauth/src/Corpsap.Oauth/Controllers/InternalCacheController.cs:16 [AllowAnonymous]
  • corpsap-oauth/src/Corpsap.Oauth/Controllers/AdmLoginController.cs:29 [AllowAnonymous]
  • corpsap-oauth/src/Corpsap.Oauth/Controllers/AdmLoginController.cs:62 [AllowAnonymous]

Why it matters. Anonymous controller actions are risky when they perform business, signing, onboarding, administration, callback, or proxy operations.

Recommended fix. Review every AllowAnonymous usage. Keep only health and externally required callbacks, and protect callbacks with mTLS/HMAC/replay controls.

HighF-04: Permissive CORS policy

Plain-English explanation. CORS controls which browser origins are allowed to call the API from JavaScript. AllowAnyOrigin plus AllowAnyHeader and AllowAnyMethod means any website can make browser requests to the API. CORS does not bypass authentication by itself, but it makes browser-based attacks easier when tokens, cookies, or weak endpoints are involved.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • corpsap-oauth/src/Corpsap.Oauth/Program.cs:85 // .AllowAnyHeader()
  • corpsap-oauth/src/Corpsap.Oauth/Program.cs:86 // .AllowAnyMethod();
  • corpsap-oauth/src/Corpsap.Oauth/Program.cs:108 policy.AllowAnyOrigin()
  • corpsap-oauth/src/Corpsap.Oauth/Program.cs:109 .AllowAnyHeader()
  • corpsap-oauth/src/Corpsap.Oauth/Program.cs:110 .AllowAnyMethod();

Why it matters. Wildcard CORS increases browser-based attack surface around token-bearing or admin APIs.

Recommended fix. Restrict origins, methods, and headers to the actual portal/admin domains required by deployment.

MediumF-05: Swagger/OpenAPI appears enabled in committed configuration or runtime code

Plain-English explanation. Swagger publishes a browsable list of API endpoints and request/response schemas. That is useful for developers, but in production it helps attackers discover hidden or sensitive routes quickly, especially when some endpoints are weakly protected.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • corpsap-oauth/src/Corpsap.Oauth/Program.cs:315 app.UseSwagger();
  • corpsap-oauth/src/Corpsap.Oauth/Program.cs:316 app.UseSwaggerUI();

Why it matters. Public API documentation can expose sensitive endpoint and model details, especially when combined with weak auth.

Recommended fix. Disable Swagger in production or protect it with admin authentication and network restrictions.
