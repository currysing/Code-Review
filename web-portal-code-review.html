HighF-01: Debug or test endpoints are present in deployable code

Plain-English explanation. debug endpoints are usually built to help developers inspect state or simulate privileged flows. They often skip normal safeguards. If they remain compiled into deployed services, an attacker or curious internal user may use them to reveal secrets, create mock security material, test downstream connectivity, or trigger operations outside the normal business path.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • web-portal/src/router/index.ts:232 component: () => import('../views/TestConnection.vue'),

Why it matters. Debug endpoints can leak configuration, exercise privileged flows, or create test security material if deployed.

Recommended fix. Exclude debug controllers from non-local builds or gate them behind strong admin auth and environment checks.

MediumF-02: Client-side auth state and route guards require backend enforcement

Plain-English explanation. a frontend route guard only hides screens in the browser. Users can still edit JavaScript, change browser storage, or call backend APIs directly. Storing bearer tokens and user profile data in sessionStorage or localStorage also means any XSS bug can read and exfiltrate them. The backend must enforce every permission even if the frontend UI tries to hide unauthorized pages.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • web-portal/src/main.ts:218 localStorage.setItem('corpIdUser', 'true')
  • web-portal/src/views/iam-smart-login-landing.vue:30 const redirectUri = useSessionStorage('iam_smart_redirect_uri', '')
  • web-portal/src/views/iam-smart-login-landing.vue:32 const headerErrorMessage = useSessionStorage('header_error', '')
  • web-portal/src/views/payment-process.vue:17 const transactionid = useSessionStorage('transactionid', '')
  • web-portal/src/views/payment-process.vue:18 const webTokenStorage = useSessionStorage('paymentWebToken', '')
  • web-portal/src/stores/languageStore.ts:10 localStorage.setItem('LANG', lang)
  • web-portal/src/stores/userStore.ts:98 const accessToken = useSessionStorage('token', '')
  • web-portal/src/stores/userStore.ts:100 const _iamSmartToken = useSessionStorage('iamSmartToken', '')
  • web-portal/src/stores/userStore.ts:102 const _iamSmartOpenId = useSessionStorage('iamSmartOpenId', '')
  • web-portal/src/stores/userStore.ts:104 const _hasCorps = useSessionStorage('hasCorps', false)

Why it matters. Browser storage and route metadata are not security boundaries. XSS can steal stored tokens/profile data, and unguarded routes can reveal workflow details.

Recommended fix. Keep backend authorization authoritative, reduce token/profile storage in the browser, add CSP, and remove hardcoded client-side access gates.

Limitations

This was a first-pass static review. I did not run the service, verify deployed ingress controls, exercise endpoints, review every business rule, or perform dependency/CVE analysis. External gateway controls may reduce exposure but do not remove risks from committed secrets, disabled validation, or debug code in deployable projects.
