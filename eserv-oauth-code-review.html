CriticalF-01: Committed credentials or key material

Plain-English explanation. the project contains passwords, client secrets, access keys, private-key material, or certificate passwords in files that are part of the repository. Source-controlled secrets are not private. Anyone with a clone, backup, CI artifact, or leaked archive can read them. Even if a value is intended for development, teams often reuse it or accidentally deploy it.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • eserv-oauth/src/Eserv.Oauth/appsettings.Development.json:17 "CorpidDb": "Server=10.68.150.241;Port=3306;Database=corpid;User Id=csql;Password=Passw0rd12#4"

Why it matters. Credentials or key material in source control should be treated as exposed. This can enable database, Redis, OAuth, certificate, or internal-service compromise if the repository or artifacts are shared.

Recommended fix. Rotate affected secrets, remove them from source control, and load values from environment variables, deployment secrets, or a vault. Add secret scanning to CI.

MediumF-02: Swagger/OpenAPI appears enabled in committed configuration or runtime code

Plain-English explanation. Swagger publishes a browsable list of API endpoints and request/response schemas. That is useful for developers, but in production it helps attackers discover hidden or sensitive routes quickly, especially when some endpoints are weakly protected.

How it surfaces in this project. The evidence below shows the concrete files and lines where this pattern appears.

  • eserv-oauth/src/Eserv.Oauth/Extensions/OauthHostApplicationExtensions.cs:71 app.UseSwagger();
  • eserv-oauth/src/Eserv.Oauth/Extensions/OauthHostApplicationExtensions.cs:73 app.UseSwaggerUI();

Why it matters. Public API documentation can expose sensitive endpoint and model details, especially when combined with weak auth.

Recommended fix. Disable Swagger in production or protect it with admin authentication and network restrictions.

SOLID Design Review

This is a static design review against the SOLID principles. It focuses on source structure, class/module size, layering, and dependency direction; it does not prove runtime behavior.

Overall SOLID posturePartially aligned. Controllers, services, repositories, gateway/cache helpers, and hosted services are separated, but OAuth and identity flows tend to concentrate validation, external calls, persistence, and response shaping in a small number of controllers/services.
Evidence reviewedThe backend scan found 2 controllers, 2 service-oriented files, and 0 repositories. Largest files include src/Eserv.Oauth/Services/EserviceTestProxyService.cs (485 lines), src/Eserv.Oauth/Gateway/GatewayRequestCryptoProcessor.cs (257 lines), src/Eserv.Oauth/Gateway/GatewayResponseTransformer.cs (247 lines).
Design strengths
  • The codebase separates HTTP controllers from services and repositories.
  • Permission, user, token, gateway, and warmup concerns are at least visible as separate files/classes.
  • This structure gives a workable starting point for dependency inversion and focused tests.
Principle-specific pressure points
  • Single Responsibility. Auth/token controllers and services should avoid mixing protocol validation, persistence, downstream calls, cache refresh, and response construction.
  • Open/Closed. New identity providers, grant flows, or gateway permission rules should be added through provider/strategy abstractions rather than modifying central controller logic.
  • Liskov Substitution. Provider-specific implementations need consistent success/failure contracts so callers can swap implementations without special cases.
  • Interface Segregation. Keep OAuth, permission, user lookup, and cache interfaces narrow; broad service interfaces make tests and replacements harder.
  • Dependency Inversion. Controllers should depend on application-level interfaces and options, not direct concrete clients or static helpers.
Recommended refactoring pathExtract provider-specific OAuth work behind small interfaces, keep controllers as request/response adapters, isolate token validation and permission resolution, and add tests around each contract.
